# Защищенная архитектура приложения v0.4

## 1. Основание проектирования

Проект: система оформления и контроля пропусков, вариант 15.

Исходная версия: v0.3. Результирующая версия: v0.4.

Архитектура разработана на основе активов, требований безопасности, модели нарушителя, модели угроз и реестра рисков версии v0.3. На этапе v0.4 проектируется размещение защитных механизмов и создается минимальный прототип компонентов безопасности. Полная прикладная реализация заявок, пропусков, базы данных и сетевого интерфейса по-прежнему не считается завершенной.

|---|---|---|---|

| Validation | app/security/validation.py | Нормализация и проверка недоверенных входных данных | Реализован прототип |

| Authorization | app/security/access_control.py | Проверка роли и разрешения на серверной стороне | Реализован прототип |
| Services | app/services/pass_service.py | Бизнес-операции только после Validation и Authorization | Реализован минимальный прототип |
| Repository | app/repositories/pass_repository.py | Изоляция доступа к данным и будущего хранилища | Определен контракт |

Разделение компонентов реализует Separation of Concerns. Пользовательский ввод, права, бизнес-логика, работа с данными, аудит и конфигурация не объединяются в одном модуле.

|---|---|---|---|
| EP-01 | Вход пользователя | Учетные данные | Authentication |
| EP-02 | Создание заявки | Поля заявки | Validation, затем Authorization и Services |
| EP-03 | Просмотр заявки | Идентификатор заявки | Authorization, Repository |
| EP-04 | Решение по заявке | ID заявки, решение, комментарий | Validation, Authorization, Services |

Неиспользуемые сетевые точки входа в v0.4 не создаются. Их наличие в архитектурной модели обозначает место будущего контроля, а не реализованный публичный API.

## 5. Доверительные границы

| ID | Граница | Потоки | Проверки |
|---|---|---|---|
| TB-01 | Недоверенный клиент - приложение | Пользовательские запросы EP-01 - EP-07 | Validation, Authentication, Authorization, ограничение допустимых операций |
| TB-02 | Services - Repository/Storage | Чтение и изменение прикладных данных | Инварианты бизнес-логики, ограниченный интерфейс Repository, минимальные права БД |
| TB-03 | Приложение - Audit | События успешных и отклоненных критичных операций | Структура события, минимальный набор полей, отсутствие секретов, защита журнала |
| TB-04 | Среда запуска - Configuration | Переменные окружения | Проверка обязательных параметров, допустимого режима и длины секрета |

Данные, пересекающие TB-01 и TB-04, считаются недоверенными до проверки. Наличие соединения через TB-02 не дает сервису неограниченных прав на хранилище. Через TB-03 передаются только события безопасности без паролей, токенов, ключей API и секретных ключей.

Последовательность обработки защищенного запроса: Interface -> Validation -> Authentication -> Authorization -> Services -> Repository -> Storage. Audit является поперечным механизмом и получает события от компонентов, в которых возникают значимые действия или отказы.

## 7. Механизм аутентификации

Архитектурно аутентификация выполняется отдельным компонентом app/security/auth.py. В v0.4 зафиксирован контракт AuthenticatedPrincipal, но проверка учетных данных еще не реализована.

Определен следующий механизм аутентификации:

- пользователь передает логин и пароль только компоненту Authentication;
- в хранилище должен находиться не пароль, а его стойкое соленое адаптивное хеш-значение; конкретная библиотека выбирается при реализации стека;
- после успешной проверки сервер создает собственный контекст аутентифицированного пользователя и серверную сессию с непрогнозируемым идентификатором;
- роль и состояние учетной записи не принимаются от клиента как источник полномочий, а определяются сервером;
- при каждом защищенном запросе сервер применяет актуальные роль и состояние учетной записи;
- после блокировки учетной записи или изменения роли старые полномочия перестают действовать не позднее следующего защищенного запроса в соответствии с SEC-15;
- пароль, хеш пароля, идентификатор сессии и иные секреты не записываются в журнал.

Выбор конкретного веб-фреймворка и технического хранилища сессий относится к последующей реализации. В v0.4 механизм определен архитектурно, но не объявляется полностью реализованным.

## 8. Модель авторизации

| Разрешение | Заявитель | Сотрудник службы безопасности | Администратор |
|---|:---:|:---:|:---:|
| CREATE_APPLICATION | + | - | - |
| VIEW_OWN_APPLICATION | + | - | - |
| REVIEW_APPLICATION | - | + | - |
| DECIDE_APPLICATION | - | + | - |
| ISSUE_PASS | - | + | - |
| CHANGE_PASS_STATUS | - | + | - |
| MANAGE_ACCOUNTS | - | - | + |
| VIEW_AUDIT_LOG | - | - | + |
| MANAGE_CONFIGURATION | - | - | + |

Проверка выполняется функцией has_permission(). Неизвестная роль получает пустой набор разрешений. Это реализует Fail Secure. Администратор приложения не получает автоматически права сотрудника службы безопасности на изменение прикладных данных.

## 9. Проверка входных данных

Модуль app/security/validation.py реализует validate_text().

Правила прототипа:

1. Значение должно быть строкой.
2. Пробелы в начале и конце удаляются.
3. Проверяется минимальная длина.
4. Проверяется максимальная длина.
5. Некорректные данные вызывают ValueError и не передаются в бизнес-логику.

Последовательность: внешние данные -> Validation -> только после успешной проверки дальнейшая обработка.

На последующих этапах для каждого поля заявки должны быть добавлены предметные проверки формата, допустимых значений и списка изменяемых полей.

## 10. Журналирование событий безопасности

Модуль app/audit/audit_logger.py реализует регистрацию минимального события:

- пользователь;
- действие;
- результат;
- идентификатор объекта, если применимо;
- прежнее и новое состояние, если они известны для операции;
- время и уровень события добавляются logging.

Подлежат журналированию:

- успешные и неудачные попытки входа после реализации Authentication;
- отказы в доступе;
- решения по заявкам;
- оформление и изменение состояния пропусков;
- изменение ролей и состояния учетных записей;
- ошибки безопасности.

В журнал не должны попадать:

- пароли;
- ключи API;
- секретные ключи;
- полные значения токенов;
- коды восстановления;
- криптографические ключи.

Прототип поддерживает поля old_state и new_state для критичных изменений, что согласуется с SEC-14. Он также удаляет переводы строк из значений полей события, чтобы отдельное входное значение не создавало поддельную строку журнала.

## 11. Хранение конфигурации

Configuration остается в app/config.py. Параметры загружаются из переменных окружения. Локальный .env исключен из Git, а в репозитории хранится только .env.example.

APP_SECRET_KEY проверяется по минимальной длине и не включается в стартовый вывод. Реальные секреты не должны находиться в исходном коде, документации или журнале безопасности.

## 14. Реализованные прототипы и тестирование

В v0.4 реализованы три модуля из перечня практической работы:

- app/security/validation.py;
- app/security/access_control.py;
- app/audit/audit_logger.py.

Дополнительно создан минимальный app/services/pass_service.py, который демонстрирует последовательность Validation -> Authorization -> Audit для операции изменения состояния пропуска.

Новые автоматические проверки:

1. Корректные текстовые данные принимаются и нормализуются.
2. Пустые данные отклоняются Validation.
3. Заявитель не имеет разрешения CHANGE_PASS_STATUS.
4. Запрещенная операция записывает access_denied в журнал безопасности.
5. Неизвестная роль получает пустой набор разрешений по принципу Fail Secure.
6. Журнал поддерживает фиксацию прежнего и нового состояния критичного объекта.

Существующие тесты стартового сообщения сохраняются. Итоговый локальный прогон после получения v0.4 должен выполняться командой:

~~~text
python -m pytest -v
~~~
